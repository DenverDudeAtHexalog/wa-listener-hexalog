WhatsApp Listener API

Read every CX group message (text, files, voice notes), get notified the moment one arrives, and, with the admin key, send messages and manage groups.

Getting started

Base URL for this server:

Read key API_KEYx-api-key: … or Authorization: Bearer …. Read endpoints also accept ?api_key=… (for EventSource and media links)Everything under "Read" below: groups, messages, media, stream, numbers, webhooks (list, create, delete) and transcripts. It cannot send or change anything on WhatsApp.

Keys are never shown on this page. Ask the CX tech owner for them and keep them out of front-end code and chat.

Identifiers. Wherever an endpoint takes a person (to, participants, mentions, sender) you can pass digits with country code (for example 919800000001) or a full JID. Group ids always end in @g.us and must be URL-encoded in paths.

Health. GET /health needs no key and returns {"ok":true,"whatsapp":"open","numbers":{"total":1,"open":1}}. It only checks the database (503 if that fails), so a green result does not mean a number is linked. Use GET /api/status for that.

Several WhatsApp numbers

The service can run many WhatsApp numbers at once, each as its own isolated login. One read key and one admin key cover all of them. GET /api/numbers lists them with their id, label, phone, state, linked, me, last_error and writes_enabled. state is one of idle, connecting, qr, pairing, open (listening), reconnecting, logged_out or replaced (the number is connected somewhere else). Numbers are added and linked in the portal, not through this API.

Reading: by default you see every number together, and a message received by two numbers (both are in the same group) appears once. Add ?number=2 (id or phone) to see only that number. Message and group objects carry number_id.

Writing: the server picks the number when it is obvious: the only one that is connected, the only one in that group, or the one that received the message you are reacting to or editing. When several could do it, you get HTTP 400 listing them; repeat the request with "number": 2 in the body (id or phone). Responses include "number" so you know which one acted.

curl -X POST "BASE/api/send/text" -H "x-api-key: $ADMIN_API_KEY" -H "content-type: application/json" \
  -d '{"to":"1203630...@g.us","text":"Hello","number":2}'

Limits and the audit log are counted per number. Live events and webhooks include number_id; connection events never include QR codes.

Message lists return {"count","next_after_uid","messages":[…]}. Filters: number (id or phone), limit (1 to 500, default 100), after_uid (newer than a cursor, oldest first, use next_after_uid), before_uid, since, until (ISO times), type (comma list: text, image, video, audio, document, sticker, location, contact, poll), sender (phone), search (text contains, case-insensitive). Without after_uid the newest messages come first.

What is recorded.

ChatsGroups only by default. 1:1 chats are recorded only if the server sets INCLUDE_DIRECT_CHATS=true. Status updates, broadcast lists and channels are never recorded.
Fieldsfrom_me is true for messages the linked number sent (also those sent through this API). media is null for messages without a file; media.stored says whether the file sits on the server or is fetched from WhatsApp when opened.
Edits and deletesA text edit updates text and sets edited_at. A delete sets deleted: true; the stored text is kept. Caption edits on media are not tracked.
Other typesContent that is not text, location, contact, poll or a file is stored with type set to its WhatsApp kind (for example pollUpdate) and no text. Poll votes are not counted.
HistoryRecent history that WhatsApp sends when a number is first linked is stored, but it does not fire webhooks or stream events. Older history cannot be requested, and messages sent while the service is down may be missed.
Same group, two numbersEach number keeps its own copy. Lists show one copy per message unless you pass number; only that first copy fires webhooks and events.

Webhooks and live stream

Create a webhook with POST /api/webhooks {"url":"https://you/hook","events":["message.created"]}. Leave events empty or out for all events. secret is optional; if you leave it out one is generated. The answer is 201 with {"id","url","events","secret"}. The secret is shown only then; listings never include it. Any http(s) URL is accepted.

Each delivery is a POST with a JSON body {"event","ts","data","delivery_id"} and the headers X-Walistener-Event, X-Walistener-Delivery and X-Walistener-Signature: sha256=<HMAC-SHA256 of the raw body>. Answer with a 2xx within 10 seconds. Failures retry with backoff (10 s, 20 s, 40 s and so on up to 1 h), 8 attempts by default, then the delivery is marked failed. Check them with GET /api/webhooks/:id/deliveries (latest 100).

The same events stream live from GET /api/stream (Server-Sent Events; optional ?number= to follow one number; ?api_key= is allowed because EventSource cannot set headers). The stream has no replay: a client that disconnects misses events, so catch up with after_uid. Webhooks are queued and retried instead.

Files and voice notes

No files are stored on the server by default. GET /api/media/:uid fetches the file from WhatsApp at that moment (through the number that received it, or another connected number that has a copy) and returns the raw bytes with the right content type. WhatsApp expires old files, after which the call returns 410; anything you must keep should be fetched when message.created fires. Other answers: 404 the message has no file, 413 the file is larger than the server's MAX_MEDIA_MB (default 50), 503 the number is disconnected. If the server runs with MEDIA_MODE=store, files are also saved to its disk and keep working after WhatsApp expires them; media.stored tells you which case a message is in.

For transcripts, run speech-to-text on your side when a webhook arrives with is_voice_note: true, then write it back with PUT /api/messages/:uid/transcript.

Safety limits

Automated sending is the quickest way to get a WhatsApp number banned. Every action goes through one queue with random pauses (1.5 to 4 s between messages, 5 to 10 s between group actions). Limits answer 429: 120 messages per hour, 10 new groups per day, 100 member changes per day (per number; the server can change them). A queue of more than 50 waiting actions also answers 429. Group actions need the linked number to be an admin (otherwise 403). Only message people who expect it. Every write is recorded in GET /api/actions.

Successful writes answer {"ok":true,"number":1,…}. Errors are JSON: write endpoints answer {"ok":false,"error":"..."} and read endpoints answer {"error":"..."}. Status codes: 400 bad input or several numbers could do it, 401 missing or invalid key, 403 wrong key for a write, writing disabled, or the number is not a group admin, 404 not found, 409 not allowed on this message (for example editing a message the linked number did not send), 410 file expired, 413 file too large, 429 limit reached or queue full, 502 WhatsApp refused, 503 WhatsApp disconnected, 504 WhatsApp did not answer in time.
